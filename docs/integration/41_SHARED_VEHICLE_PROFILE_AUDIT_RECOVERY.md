# Shared vehicle profile, audit and owner recovery

Status2026-10-05: compatible public SDK and API contract published; scoped COP API production deployment completed2026-10-05T19:34:00UTC. No actual user vehicles, records, identity, membership or calls changed for acceptance. JSON OpenAPI remains binding; no new endpoints.

## Owner-declared routing profile

SharedVehicleDetails.routingProfile is optional for legacy data: version1,mappedProfile exact sim-mapped-road-profile-v1,powertrain combustion|electric|plugInHybrid. Mapped fields retain intent car|commercial_truck|car_with_trailer|road_legal_4x4, heightM/widthM/lengthM in meters, loadedWeightKg/axleLoadKg in kilograms, axleCount, attached trailer facts. Whole-combination dimensions and weight must include the trailer and bound its facts. Nontruck axle fields and private-access authorization are not accepted. The schema plus semantic SIM request rules validate stored profile. Only owner changes its contents; a missing or unsupported existing profile on update causes409 rather than loss. Driver may keep identical profile while updating an otherwise permitted ordinary detail. Older cars without profile remain explicitly unknown, never silently car.

This is an authenticated current owner declaration, not proof of physical dimensions or legal clearance. Recipient fetches current vehicle/dataRevision in authenticated account scope, checks sharedRoutingProfileVersions[1] and routing capabilities, preserves every mapped request field, and still verifies SIM assessment for every actual route. Absent/stale/unsupported/unavailable data cannot choose default car or a direct alternate provider. SIM contract and graph are unchanged.

## Exact owner recovery

Create/Update optional ownerBinding input(version1,localVehicleId UUID) identifies owner Vehicle.id preserved in its local/cloud backup. Server derives ownerAccountId from authenticated session, checks current owner role and exact CAS on update, and serializes uniqueness under owner lock. One active owner vehicle cannot map to two sharedVehicleIds. Conflicts409OWNER_BINDING_EXISTS/CONFLICT require authenticated refresh, never another create or name/SPZ matching.

Read-only ownerBinding(version1,localVehicleId,ownerAccountId) is returned on list/get/create only to current matching owner, never recipient/sync vehicle events. After ownership transfer old mapping is no longer returned to either owner; new owner explicitly establishes own binding with current CAS. Account switch and new phone must use fresh authenticated list and matching ownerAccountId/role. Unsupported binding stays unknown. Existing vehicles without binding require explicit owner confirmation against a known sharedVehicleId and UUID; the server cannot infer a lost link from name/plate. Deleted vehicle/membership is never resurrected. No private backup upload or history migration.

## Audit corrections and voids

Use existing recordWrite and recordDelete. RecordWrite optional correction(version1,recordId,recordRevision,reason) identifies the reviewed base. Existing edit uses same recordId, exact expectedRecordRevision,dataRevision,membershipRevision and original author; next revision and changed fields are one operation. Odometer correction uses new recordId plus data.correctionOfRecordId/correctionReason pointing to reviewed original, and matching correction target revision/reason. Original observation remains in history and is excluded by correction rules. Do not change tripId or erase typed receipt details.

Wrong correction base409CORRECTION_BASE_CHANGED or ordinary CAS409 requires user-reviewed refresh; do not rewrite a durable request under same operationId or silently rebase. Retry unchanged request returns original receipt, including optional recordRevision plus eventSequence; it must not overwrite newer cached state.

Every new record event gets immutable audit(version1,action create|correct|void,operationId,previousRecordId?,previousRecordRevision?,reason?). Sync event author is acting account; record author stays original author. Original payload remains in prior immutable event. Existing old-client edits still have exact CAS and retained revisions; absent user-supplied correction reason is not invented. recordDelete is logical void, not removal of history: reason is stored in void audit, original payload remains on tombstone and old events. Current mileage/care/statistics fold latest nondeleted state and recompute, never add all historical revisions. Cost payload/audit events remain behind readCosts. Active vehicle history retains existing policy; whole-vehicle deletion is purged after30days, operation receipts expire after30days with replay guard. Do not claim indefinite forensic retention.

## Current care reminders

Vehicle.activeCareReminders(version1,dataRevision,state complete|unavailable,items) contains all current nondeleted incomplete reminder records, no expense/service prices, history or passengers/GPS. Item fields recordId,recordRevision,title,dueAt UTC ISO8601?,dueOdometerKm decimal kilometers?. No implicit recurring rule is synthesized; current contract is one due date/distance per reminder, completion explicitly recorded. More than500 or invalid records returns unavailable/empty, never truncated complete. Empty complete means no active reminders; unavailable/absent/stale does not mean remove all saved notifications. Recipient readVehicle grants same current care snapshot; manageReminders still gates writes. Current authoritative odo is separate version2 field under same dataRevision; estimated value must remain labelled and cannot be declared an instrument reading. New host schedules own notifications only with permission/current scope/current complete snapshot, deduplicating stable recordId and cancelling old-account/membership notifications. No startup full cost-history fetch needed.
